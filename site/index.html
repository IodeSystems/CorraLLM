corral + LLM

One OpenAI-compatible API in front of every model you run or pay for.

A reverse proxy, model lifecycle manager, and priority/fairshare scheduler with cost-aware overflow. It starts and stops local llama.cpp models, forwards to paid upstreams, and decides who is served, where, and at what cost, based on the caller's key.

why it exists

One GPU, several callers, some paid overflow.

A chat model, an embeddings model, an interactive coding agent, and a batch indexer all want the same card. Without a scheduler the batch job fills every slot and the person typing waits.

corrallm sits in front. Each API key maps to a priority group; requests are admitted by weighted fairshare over each backend's slots. When a backend is full a request queues, is rejected, spills to another backend, or preempts a lower-priority one. Every request is costed in dollars, local energy included.

Callers keep using the OpenAI API. corrallm does the rest.

  • Any OpenAI client works: set a base URL and a key.
  • Local models load on demand and evict by cost.
  • Overflow goes to paid upstreams only where a group allows it.
  • Streaming is preserved.

what it does

The gateway, the lifecycle, the scheduler.

Everything here is in the README and runs in production fronting a mixed embeddings and chat workload.

OpenAI-compatible

/v1/chat/completions, /v1/completions, /v1/embeddings, /v1/rerank, /v1/models, and the audio endpoints (speech to text, text to speech, realtime, optional diarization). /v1/capabilities lists what a given deployment serves.

Anthropic Messages

/v1/messages serves the Anthropic Messages API next to the OpenAI endpoints.

Model lifecycle

Starts a backend's command on demand and waits for a real health check, not an open port. Capacity is a vector of memory pools (per-GPU VRAM, system RAM); a model loads only if it fits every pool, and idle models are evicted to make room. Pause takes a model out of service until resumed.

Fairshare scheduling

Priority groups with a weight, interruptibility, and a per-backend saturation policy. A key can be granted other groups and pick one per request. A caller can reserve a few slots so interactive work keeps headroom against batch.

Cost-aware overflow

A served model lists its backends in order. A group can opt into a lower quality tier, with an optional maxTokens clamp. Everything resolves to dollars: local energy, paid usage, and the energy spent loading a model.

Spend and budgets

Spending limits over a sliding window per group; keys mint child keys with a share of their budget. Every text reply carries usage.cost and usage.cost_source, and every request records dwell time, tokens, and cost.

Guardrails and backpressure

Guardrails are set per root key, default-on or opt-in, including loop detection on streamed chat replies. A saturated caller gets a 429 with Retry-After from a measured dwell average, plus X-RateLimit-* headers. Refusal codes are documented in /v1/capabilities.

Dashboard

Models, lanes, live admission load, per-key usage (cost, requests, energy), queue pressure, backend logs, and on-demand load and unload, streamed over SSE.

Prompt-cache affinity

For a llama.cpp model, a conversation keeps its slot, and its warm KV cache, across turns. The conversation is the request's standard prompt_cache_key. How, and who else supports it.

prompt-cache affinity

Same conversation, same slot.

A llama.cpp server keeps one KV cache per slot. A turn that lands on a different slot recomputes the prompt. With slotAffinity or slotAwareDequeue set on a model, corrallm picks the slot per conversation and tells the client which one it chose in X-Corrallm-Slot.

The conversation is the body's prompt_cache_key, else the X-Corrallm-Conversation header, else inferred from the head of the prompt. A declared id is scoped by the caller's key, and the body goes upstream unchanged. corrallm reads usage.prompt_tokens_details.cached_tokens from the reply, falling back to llama.cpp's timings.cache_n.

No new client field to learn.

  • prompt_cache_key is already sent by some clients and accepted by several providers (table below).
  • The slot header is informational; nothing requires a client to read it.
  • Without a key, affinity falls back to inference, so unmodified clients still benefit where the prompt head is stable.

install

One command, then a config.

Linux (amd64, arm64) and macOS (Apple silicon).

$ curl -fsSL https://corrallm.iodesystems.com/install.sh | sh
$ corrallm service install -- --config ~/corrallm.yaml

Installs corrallm, llm-bench and llm-bench-mcp from the latest release to ~/.local/bin. Needs minisign: it checks the release signature and the archive's sha256, and installs nothing if either fails. Refuses to run as root. Starts nothing. Read the script.

$ git clone https://github.com/IodeSystems/CorraLLM.git && cd CorraLLM
$ make install     # builds the UI and the binaries into ~/.local/bin

Needs Go, Node and pnpm.

corrallm service install writes a systemd user unit on Linux and a launchd LaunchAgent on macOS; everything after -- goes to corrallm serve. On Linux, run loginctl enable-linger "$USER" so the service survives logout. On first run an admin token is generated at home/admin.token; the dashboard, served at the same address, asks for it. The default listen address is :6502.

  • Local models run on llama.cpp's llama-server, which you build or install yourself: a C/C++ compiler, cmake and git; on NVIDIA, the CUDA toolkit and driver; on macOS, Metal.
  • Paid upstreams need none of that: a backend with no command is a pure proxy to an OpenAI-compatible endpoint.

Verify a release yourself

Each release has a SHA256SUMS file, signed with minisign, key ID 2CC27A171DE03D42 (shared with dun and para). Get the key from this site (minisign.pub), compare the ID, then verify:

$ curl -fsSLO https://github.com/IodeSystems/CorraLLM/releases/latest/download/SHA256SUMS
$ curl -fsSLO https://github.com/IodeSystems/CorraLLM/releases/latest/download/SHA256SUMS.minisig
$ minisign -V -p minisign.pub -m SHA256SUMS

Archives are named corrallm_<os>_<arch>.tar.gz (linux_amd64, linux_arm64, darwin_arm64), the same in every release. Versioned copies sit beside them.
